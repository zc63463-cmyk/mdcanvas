## 一、先回答两个问题

**需要改架构代码吗？需要，但只改已暴露问题的边界，不更换整体技术路线。**

保留 `.mm.md → kernel → React → 产品宿主`。近期重点是：文档根与布局根分离、多中心约束、引用一致性、拖拽事务、渲染后端能力契约。它们不是拆文件美化，而是直接避免节点重复、关系线消失、位置丢失的结构修正。

**需要采用 Godot 吗？现在不需要，也不建议。**

当前需求是文本编辑、树形生长、多中心摆放、自由连线、资产引用和跨平台打开。Godot 能做这些，但不会自动实现本项目的文档协议、锚迁移、自动布局、撤销事务、浏览器文件授权。改用 Godot 会引入另一套语言/运行时、输入编辑链路与导出适配，并没有证据证明能降低下一阶段总成本。

**Project Graph 值得学，但它不是 Godot 项目。** 实际应用依赖 React/TypeScript、Canvas 2D、Tauri 2；应用 package.json 声明 GPL-3.0-only。学习交互与设计模式，直接复用代码前核查许可证义务，不把“开源”理解为无条件复制。

## 三、本轮实证：测试绿不代表集成边界正确

### 运行结果

- kernel：`layout-forest.test.ts` 14 条、`links-visibility.test.ts` 4 条、`viewport-cull.test.ts` 3 条，共 **21/21 通过**。
- react：`centers.test.ts` **27/27 通过**。
- 对 react 与 canvas 的 TypeScript project-reference 构建检查命令成功结束，无诊断输出。
- 没有运行全量 gate、浏览器回归或真实交互帧率压测。上述结果不能称为“全部验收通过”。

### 探针 A：深层节点升格造成布局重复——确认

构造 Root→A→C 与 Root→B，仅升格 C。执行 collectCenters→buildCenterSpecs→layoutForest，结果为 **5 个布局条目，4 个唯一节点 ID**。

原因：菜单只排除了根，没有限定一级子节点（`contextMenuItems.ts:111-129`）；buildCenterSpecs 只从根的直接 children 里剔除升格节点（`pipeline.ts:222-234`）。C 仍留在 A 子树中，同时又被作为独立中心加入。

**修法**：近期坚持已确认的一层中心约束。在领域操作入口校验 parentId=root.id；读取外部文档时也要校验并给诊断，不能只隐藏菜单。若以后支持深层中心，再设计树投影裁剪，而不是放宽一个 if。

### 探针 B：所有一级分支升格后文档自由边失去数据入口——确认

给文档根挂一条 edges，再将 A、B 全部升格。布局首个 depth=0 节点的 note.edges 是 `undefined`，原始文档根的 edges 仍有 **1 条**。

原因：`MapView.tsx:415-416` 由 `layout.nodes.find(depth===0)` 反推文档根并 collectFreeEdges；而 `pipeline.ts:227-228` 在没有剩余普通分支时不再输出虚拟文档根。更隐蔽的是部分升格时虚拟根只含剩余 children，也不能替代完整文档进行关系解析。

**修法**：显式传入真实 documentRoot，文档级 edges/centers/锚解析始终使用完整文档；layoutForest 输出只负责可见几何。不要再从渲染树反推事实源。该探针验证数据链路，未声称已做浏览器截图复现。

### 探针 C：中心改名后引用悬空——确认直接改名路径

将 A 改成 Renamed 而保留中心 `at: node:Root/A`，collectCenters 返回 `dangling`。`note-anchor.ts:113-148` 按文本逐级匹配；`controller.ts:131-134` 的 updateText 只改标题。

**修法**：统一引用索引与重命名/移动事务。必须区分两类路径：UI 的索引路径会受重排影响；文档文本路径会受改名/同名影响。它们都不是永久 ID。

优先为应用内改名/移动维护受影响锚，并把节点变更和锚变更合成一个 undo；外部手工编辑仍须悬空/歧义诊断。若跨文档稳定身份成为硬需求，再引入可选持久 uid，不能直接让全文件充满 ID。现有路径可作为兼容与可读回退。

### 探针 D：实际中心协议可以往返——通过基础样例

将 centers 对象数组 serializeMm→parseMm 后，`at/dir` 保留。这说明基础中心协议不需要换成二进制，也不应凭“YAML 不支持任意嵌套”断言现有数组不可用。本轮未覆盖中心所有字段/转义/非法数据的完整往返矩阵。

## 四、分级改造建议

> P0 表示多中心功能发布阻断项，不表示已证明文件被永久破坏；P1 表示下一阶段可靠性/体验建设；P2 表示证据触发的优化。

| 级别 | 改什么 | 为什么 | 验收标准 |
|---|---|---|---|
| P0 | 文档根与几何根分离 | 森林布局破坏单根推断 | 全部/部分升格时跨中心边与诊断不丢 |
| P0 | 中心资格与投影唯一性 | 深层升格重复节点 | 每个文档节点至多一个布局实例；非法中心有诊断 |
| P1 | 引用一致性事务 | 文本路径并非永久稳定 | 改名/移动/撤销后 centers、center_pos、edges 一致；同名不误指 |
| P1 | 中心拖拽动作链 | 当前手势释放仍走结构 move-node | 中心拖拽只改坐标；普通节点仍重排；一次拖动一次undo；Esc取消 |
| P1 | 双后端能力清单 | Canvas 不是 SVG 的等价替代 | 切换前明确自由边/资产/note/方向连线的保真与降级提示 |
| P1 | 资产持久化宿主 | objectURL 刷新失效 | 上传→保存→关闭→重开仍能解析；授权撤销/重名/写失败有明确处理 |
| P2 | 路由与可见性解耦 | 可见边集变化会使路由memo失效 | pan/zoom 不改变静态路线；跨视口曲线不被误裁 |
| P2 | 中心局部布局缓存 | 森林路径目前全量重算 | 同一真实负载测出收益再引入；避免提前造脏图系统 |
| P2 | 菜单/快捷键共用命令描述 | 新功能入口易语义漂移 | 同一动作共享执行、可用条件、标签与帮助 |

中心拖拽证据：`useMapGestures.ts:240` 调用 onNodeMove(plan.op)，当前已读链路没有中心坐标分支；菜单升格调用只给 dir（`NodeContextMenu.tsx:101`）。应标为“坐标读写工具已有，交互闭环未见”，不是“自由摆位完成”。

几何还有一个需补测试的风险：`forest.ts:104-113` 把根中心放在 cursorX，再按子树宽推进；未考虑根到左右 bounds 的偏移差异，也未给手工中心预留占位。向左/向右混排与手工/自动混排不保证不相交。可以设计明确的自动排布基准与手工重叠策略，不必使用物理引擎。

## 五、性能问题要分层，不要统称 SVG 慢

当前链路已经有节点/树边/自由边裁剪，但其语义不同：

1. 树边按任一端点可见保留（`kernel/src/layout/cull.ts:47-58`），两端都在外部而线穿屏幕的情形会被忽略。
2. 自由边按两端盒的包围盒裁剪（`MapView.tsx:508-523`），改善跨屏长边，但**端点包围盒不等于贝塞尔曲线包围盒**；大弧外鼓仍需保守边界或缓存路线 bounds。
3. 自由边只对可见集路由，但可见集依赖视口。`FreeEdgeLayer.tsx:139-175` 的路由依赖 edges，并按已路由边累积交叉罚分。平移改变可见集时，既可能重算，也可能改变剩余边路线。不是“有 useMemo 就绝不重算”。
4. 森林管线明确跳过 LayoutCache（`pipeline.ts:178-182`）。应拆分静态子树布局、中心位移预览与最终路由，不要每帧完成整套持久化。
5. Canvas 简化 scene 输入只有节点与树边（`sceneBuilder.ts:17-34`）；自由边只在 !useCanvas 分支渲染（`MapView.tsx:918-924`）。**不能因为切换后快了，却悄悄少画内容，就称性能升级成功。**

建议性能协议（这是未来验收目标，不是本轮实测）：同一文档用 500/2,000/10,000 节点，配 0/100/500 条真实分布关系边、长文本与附属区；记录 p50/p95 的布局/路由/渲染/交互延迟、峰值内存与空闲CPU。拖拽目标帧预算可先取 16.7ms，连续超预算再定位。优先缓存与批处理，然后对等比较现有 SVG/Canvas；DOM/GPU 才是瓶颈时才讨论 WebGL。

## 六、Godot 的收益与真实代价

### 能带来什么

成熟的场景变换、2D/3D 绘制、动画系统、原生打包和输入事件系统。若未来转成原生优先、持续动画、3D/XR 空间知识编辑器，它是有意义的候选。不能说 Godot 只能做游戏。

### 不能替你解决什么

- Godot 的场景树是运行时对象生命周期，不等于 `.mm.md` 文档树。
- 画布连线/节点控件不等于满足本项目语义的自动树布局与避障。
- 引用失效、中心投影、事务撤销是业务正确性，与 GPU 无关。
- Web 导出仍受浏览器文件访问限制，不会因使用引擎而获得任意目录权限。
- Markdown 富文本、中文组合输入、焦点、剪贴板、可访问性、SVG 导出仍需迁移适配与回归，不是说 Godot 不支持中文。

官方 4.6 Web 导出文档明确：需要 WebAssembly/WebGL 2.0，使用 Compatibility 渲染；Godot 4 的 C# 项目当前不能导出 Web；单线程可用且为默认，不必隔离头，多线程则有跨源隔离要求。因此不能笼统说“Godot Web 都需要特殊服务器配置”。这些是所查 4.6 文档结论，不声称覆盖未来版本。

### 方案成本矩阵

| 成本/能力 | A 现栈局部修正 | B 现栈+桌面宿主 | C Godot主客户端 |
|---|---|---|---|
| 引用与中心语义修复 | 必做 | 必做 | 仍必做：共担成本 |
| 自动布局/避障规则 | 复用 | 复用 | 移植或跨运行时桥接 |
| 当前 React 文本与面板 | 复用 | 多数复用 | 重建或维护双UI边界 |
| 文件能力 | 浏览器授权+降级 | 新宿主能力/安全权限 | 原生可增强，Web仍受限 |
| SVG导出与测试 | 复用并补齐 | 复用并补平台回归 | 重做适配，业务fixtures可保留 |
| 新构建/维护面 | 小 | Tauri/Rust/更新签名 | 引擎/语言/渲染/输入/打包 |
| 当前推荐 | **是** | 原生文件需求验证后 | **否，仅独立验证候选** |

既有代码行数只是迁移暴露面，不是“全得重写”的估算。kernel 4,480行可在浏览器 JS 桥中保留，但 Godot 原生版的同一复用路径不免费；React层也能留作DOM覆盖，但会新增坐标/焦点/状态同步。真正要比较的是未来新增成本和长期收益，不是因为已经写了代码就永远不准换。

粗粒度规划区间（单人熟悉现栈，非承诺，不能简单相加）：上述P0边界修复连回归约2–5人日；完整中心拖拽/引用一致性约4–10人日；目录授权宿主约3–8人日；Godot对照原型约5–10人日只能回答可行性，不能交付等价产品。等价迁移牵涉至少输入、领域桥、渲染、路由、导出、宿主、回归七个工作包，应按数周至数月级风险评估，不给虚假的精确排期。

## 八、建议的目标结构与实施顺序

保持现有三包，不先新建包或引入DI：

- 文档层：真实 root、edges、centers、center_pos 与引用索引。
- 命令层：统一 apply/undo；加中心升降/位移、重命名引用迁移的原子事务。
- 布局层：单树/森林→稳定几何；一层中心验证；视图投影不冒充文档。
- 场景层：布局/路由结果→后端无关场景与能力描述；已有 backend/sceneBuilder 是起点。
- 展示层：SVG 主路径、Canvas 明示降级、DOM文本与面板。
- 宿主层：浏览器文件与AssetHost；未来可选桌面宿主。

第一批先开问题单并冻结复现样例：深层中心重复、全部升格自由边、改名悬空、双后端降级。第二批修文档/几何根边界与中心资格。第三批补中心拖拽与一次undo、引用迁移和保存重开。第四批做真实负载性能协议，证据触发路由缓存/后端深化。原生目录能力若比图形吞吐更痛，应优先考虑桌面宿主而不是Godot。

## 九、什么条件下反转结论

仅在这些条件同时得到证据时，才重新评估 Godot：

1. 产品明确转向原生优先的空间/3D/高动态工作台，Web轻量访问不再核心；或现有渲染在必需负载上有已证实、无法经济修复的瓶颈。
2. 在同一数据和功能保真要求下，Godot原型明显胜出现有SVG/Canvas方案，而不是只比“画矩形”的演示。
3. 中文输入、编辑、导出、持久化、撤销的关键验收均通过，收益不是靠省功能换来的。
4. 有持续维护引擎客户端的资源，接受过渡期双栈成本。

**最终建议：改局部结构，不改产品根基；先保证多中心是一份文档的可靠视图，再增加操作能力。当前无需采用 Godot。**
