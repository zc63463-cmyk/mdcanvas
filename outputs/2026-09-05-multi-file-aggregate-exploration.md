# 多文件图聚合展示：思路探索验证

日期：2026-09-05 · 性质：设计探针（不写产品代码）· 结论：**支持，且与布局岛模型同构，建议作为其统一泛化而非平行新系统**

## 1. 结论

多文件聚合展示（主文件 + 附属文件）在现有架构上**可行且低成本**，因为它就是「布局岛」的跨文件特例：

- 每个文件的根 = 一个独立中心（升格节点的跨文件类比）
- 附属文件 = 携带自己子树的断裂子树的**天然承载**——文件边界即岛边界，owner 按文件归属天然唯一，不存在文档内递归投影的「节点重复」风险
- 用户直觉「符合文件逻辑」是对的：每个文件仍是独立合法的 `.mm.md`，可被旧版本和外部编辑器打开，纯文本事实源原则不破坏

并且它为布局岛 G2（切下子树的持久化承载）提供了**第三条路径**：`detach-to-file`——切线时把子树导出为新文件 + 主文件记一条 attach，绕开了「移到文档根承载导致 heading 层级变化 + 引用迁移」的成本。

## 2. 同构映射（布局岛 → 多文件聚合）

| 布局岛概念（文档内） | 多文件聚合 | 差异 |
|---|---|---|
| 升格中心（centers） | 主文件根（默认中心） | 主文件无需元数据标记 |
| 断裂子树根（detached） | 附属文件根 | 跨文件天然独立承载，无 G2 层级问题 |
| center_pos 坐标 | `root.note.attach[].x/y` | 坐标存主文件（sidecar 精神，附属文件零污染） |
| 递归投影 + 唯一 owner | 聚合投影 = 各文件各自成岛 | owner 按文件归属，**不可能重复**（比 A1 简单） |
| 跨区域边界线（G3） | 主-附文件视觉连接线 | 可选；G5 决策门 |
| 路径锚 dangling | 文件重命名/移动 → attach 悬空 | 同构问题，诊断三态可复用 |

## 3. 探针实证（2026-09-05 实测，kernel dist）

**探针 1 — 扁平对象数组（与 centers 同构形状）**：

```
<!--
attach:
  - doc: 附属A.mm.md
    dir: right
    x: 400
    y: 120
  - doc: sub/附属B.mm.md
    dir: down
-->
# 主文件
```

- 解析：`root.note.attach` 结构化还原 ✅，零诊断 ✅
- round-trip 安全闸（`verifyRoundTrip`）通过 ✅
- 根 note 必须位于 **H1 之前**（「其后第一个结构节点」绑定语义）

**探针 2 — 嵌套结构走内联 JSON**：`attach_meta: {"version":1,"files":[{"doc":...,"tags":["a","b"]}]}` 无损往返 ✅（自研 YAML 不支持嵌套 mapping，但对象值以 `JSON.stringify` 内联承载——serializer.ts `yamlField` 已支持）

**探针发现的两个真实风险点**（必须写进实现验收）：

1. **坐标解析为字符串**：`x: 400` 解析回 `"400"`（string）。自研 YAML 不做标量类型转换。读取侧必须 `Number()` 强转 + `Number.isFinite` 校验 + `0` 是合法坐标——与 centers.ts 的 `num()` 现状一致，新字段沿用同款防御。
2. **笔记块位置陷阱（无诊断静默错绑）**：笔记块写在 H1 与 H2 之间会绑到 H2 节点且**不产生任何诊断**（探针实测）。主文件的 attach 必须写在 H1 之前。编辑器写路径（`updateNote`）天然正确，但用户手编/外部编辑器写错位置时，聚合配置会静默落在子节点上——需要一条「root note 位置校验」诊断或在读取侧兼容降级（找不到根 attach 时提示）。

**探针 3（反例，顺带证实诊断链工作正常）**：非 canonical 格式（`<!-- attach:` 同行）会产生 W-STRAY-LINE 并把行内容升级为 heading——说明诊断链能捕获格式错误，但**不能**捕获位置错误（风险点 2）。

## 4. 既有架构核查（源码事实）

| 事实 | 证据 | 对聚合的影响 |
|---|---|---|
| 实体引用 `@kind:id` 是**单文档**解析 | `buildEntities(refs, GATEWAY_TITLES)`，title 表是硬编码常量（MindmapStage.tsx:164） | 跨文件实体解析不存在，Phase 0 不涉及 |
| 文档模型是单文档 controller + OpHistory | `MindDoc` / `applyDoc` 带 dirty 守卫（useDocumentActions.ts） | 跨文件原地编辑 = 大改；只读聚合 + 跳转打开 = 复用现链路 |
| `MapView.documentRoot` 纪律已立 | 复审修复：文档根 ≠ 几何根（多几何根场景自由边/折叠路由必须读完整树） | **直接支撑聚合**：layout 传聚合投影、documentRoot 传主文件根，自由边收集不错根 |
| `layoutForest` 多中心合并已存在 | forest.ts：局部布局 → 平移 → 重建 links | 聚合投影是其上游变体：centers 来自不同文件的根 |
| 折叠路由需完整树 | `freeEdgeEndpoints(edge, boxOf, root, collapsed)` | 聚合下跨岛折叠代理需新规则（见风险） |
| Canvas 后端不渲染自由边 | FreeEdgeLayer.tsx 文件头注明 | 聚合场景的自由边限制同此，不新增债务 |

## 5. 分层设计建议

### L1 协议层（主文件 root note，H1 之前）

```yaml
attach:
  - doc: 附属A.mm.md        # 相对路径锚（禁止绝对路径，保证目录可整体迁移）
    dir: right              # 生长方向（复用 GrowDir 四向）
    x: 400                  # 可选；缺省自动排列（与 centers 同语义）
    y: 120
```

- 主文件只存**位置与方向**，不复制附属内容（事实源唯一）
- 读取兼容：未知字段容忍（parser 已支持），旧版本打开主文件只是忽略 attach
- 降级注意：旧版本**保存**主文件会保留未知字段吗？——会（note 透传），但需验证（A0 探针清单）

### L2 聚合投影层（kernel 纯函数，零 DOM）

```ts
projectAggregate(
  mainRoot: EditableNode,
  attach: readonly AttachSpec[],           // 经校验的 attach（坐标强转后）
  loadDoc: (docPath: string) => EditableNode | null,  // 宿主注入；null → dangling 诊断
): { centers: CenterSpec[]; attachments: Map<string, EditableNode>; diagnostics: Diagnostic[] }
```

- 输出直接喂给现有 `layoutForest`（主根 + 各附属根皆为 CenterSpec）
- 归属集合：渲染/命中需要知道「节点属于哪个文件」——`Map<nodeId, docPath>`（附属文件渲染只读、点击跳转的依据）
- 循环 attach（A 挂 B、B 挂 A）检测：按 docPath 集合去重 + 诊断，不递归展开

### L3 交互层（react / apps/canvas）

- **Phase 0（只读聚合）**：附属岛渲染但不可编辑（拦截编辑手势）、不可拖；文件根节点带「文件徽标」视觉区分；双击文件根 → `applyDoc` 打开该文件（复用 dirty 守卫链路）
- **Phase 1（位置可拖）**：附属文件根进入 `centerIds`（同源派生纪律），拖动 → 写主文件 `attach[].x/y`——**唯一可写路径仍是单文档**（主文件），OpHistory 单文档 undo 完整有效，不需要跨文件事务
- **Phase 2（切线到文件，依赖 G2 批准）**：切下子树 → 导出为新 .mm.md + 主文件记 attach；接回 = 读入文件内容替换 attach 记录（显式操作，delete 文件与否由用户决定）
- 不在路线图内：**Phase 3 跨文件原地编辑**（需要多文档 controller + 跨文件 undo，与「自用摩擦驱动」纪律不符，除非出现 ≥2 条真实摩擦）

## 6. 新增决策门（与 G1–G3 并列，批准前只派探针）

| 门 | 问题 | 推荐 | 代价 |
|---|---|---|---|
| G4 | 附属位置存哪 | **主文件 root.note.attach**（sidecar 精神，附属文件零污染） | 主文件成为聚合视图的拥有者；主文件丢失 = 布局丢失（内容不丢） |
| G5 | 跨文件边要不要 | 暂不做；先做同文件自由边 + 视觉连接线（不参与布局/导出语义） | 跨文件锚 `doc:file/path` 是 A2 引用迁移的放大版（文件重命名 + 路径歧义） |
| G6 | 编辑语义 | 附属只读 + 双击跳转（Phase 0/1） | 用户想在聚合视图直接改附属内容时要多一步 |

## 7. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 文件重命名/移动 → attach dangling | 高 | 诊断三态复用；Phase 0 只提示不自动重绑；后续可做「同目录同名匹配」修复向导 |
| 根 note 位置陷阱（静默绑到子节点，无诊断） | 高 | 新增诊断或读取侧兼容；写进 A0 验收（探针已实证） |
| 附属文件被外部修改 → 聚合视图过期 | 中 | DocumentHost 侧 mtime/handle staleness 检测；Phase 0 提供手动刷新 |
| 循环 attach / 重复 attach 同一文件 | 中 | projectAggregate 去重 + 诊断 |
| 大聚合性能 | 中 | 视口裁剪/LOD 已有；聚合节点数超阈值时 Canvas 后端无自由边（既有边界，如实声明） |
| 坐标字符串化 | 低 | num() 同款强转 + 有限数校验（探针已实证） |
| 折叠跨岛代理语义 | 低 | 折叠是文件内概念，跨岛不做代理（附属文件根的折叠只影响其自身子树） |

## 8. 与布局岛路线图的衔接

- **不阻塞** A1–A6：聚合投影是 layoutForest 的上游变体，A1 的递归投影与之正交（A1 解决文档内任意深度，聚合解决跨文件）
- **互相成就**：复审修复的 `MapView.documentRoot` 纪律正是聚合渲染的前置条件（已立）；`centerIds` 同源派生纪律直接适用于 Phase 1
- **G2 第三路径**：detach-to-file 进入 G2 决策门作为候选方案对比（vs 文档根承载）
- 建议把本文作为 design 文档的 **v1.5 增补章节**引用，不另起设计体系

## 10. 增补（2026-09-05 晚）：聚合态编辑的可行性纠正 + 升格id 身份层

### 10.1 纠正：聚合态编辑**可以做**，原「Phase 3 不进路线图」是价值判断不是技术不可能

关键洞察：**节点编辑永远发生在单个文件内部**（一个节点只属于一个文件），因此不需要跨文件事务。方案为「多控制器路由」：

- DocSessionRegistry：每文件一个 EditorController（聚合视图与单独打开共享会话）
- 命中 → (docPath, nodeId) → 路由到该文件 controller.apply(op)——现有 TreeOp 零改动
- 全局 undo 协调器：操作日志记 docPath，Ctrl+Z 委派到对应文件的 OpHistory（redo 失效语义需设计）
- 保存编排：每文件 dirty + save-all
- 自相似性质：附属文件自身就是合法布局岛文档（内部 centers 自治），聚合只是外套一层森林

成本 3–6 人日；主要风险在 undo 协调语义与保存编排，不在布局或协议。

### 10.2 用户提案：升格id（cid）——子树持久身份层

给升格子树根节点笔记写稳定编号 `cid: c7`，root.note 登记 `centers[].cid` 与 `next_cid` 计数器。**价值超出 agent 寻址本身**：

1. **agent 精确定位**：grep `cid: c7` → 其后第一个 heading = 子树根 → 读至同级/更浅 heading 止。纯文本友好，零工具依赖。
2. **根治路径锚 dangling（复审确认的既有硬伤）**：cid = 身份，`at` 路径降级为可过期的位置提示；A2 引用迁移从「路径匹配」变为「按 cid 重新生成 at」，改名/移动不再悬空。
3. **复制编码工作流**：右键「复制中心编号」→ 粘贴给 agent/协作者，与规划中的「复制选中子树」功能同源。

**设计契约（草案，待进布局岛 A0）**：

| 项 | 约定 |
|---|---|
| 存储 | 节点笔记 `cid: c7`（身份在节点上，人/agent 可见）；root.note.centers[].cid 关联布局元数据；root.note.next_cid 单调计数 |
| 生成 | 文档内顺序分配，**永不复用**；单写者无冲突 |
| 稳定性 | 分配后随节点存续，改名/移动/降格不回收；节点删除即消失（无墓碑） |
| 解析优先级 | cid 优先，at 为提示；读取侧 dup cid → first-wins + 诊断 |
| 粘贴语义 | 跨文件/跨文档粘贴子树时重新分配 cid（paste-as-new-identity），防冲突 |
| 序列化 | cid 为标量，note YAML 既有机制覆盖，round-trip 无新风险（探针 1 已验证同构形状） |
| 视觉成本 | 仅升格子树有 cid 笔记块，普通节点零噪音 |

### 10.3 决策矩阵（单文件+升格id vs 多文件聚合可编辑版）

| 维度 | 单文件 + 升格id | 多文件聚合（可编辑，§10.1） |
|---|---|---|
| 聚合态编辑 | ✅ 现有机制直接可用 | ✅ 需 3–6 人日（undo 协调/会话注册/保存编排） |
| agent 子树寻址 | ✅ cid 单文件 grep | ✅ 需 doc+cid 双重寻址（也可行） |
| undo / 保存 | ✅ 单栈单文件 | ⚠️ 全局协调器 + 多文件保存编排 |
| 一份子树进多个聚合视图 | ❌ | ✅ 独占能力 |
| 独立分享 / 独立生命周期 | ❌ | ✅ 独占能力 |
| dangling 风险 | cid 根治 | cid + 文件路径双重风险 |
| 协议改动 | 小（cid + next_cid） | 中（attach + 归属表 + undo 协调） |

### 10.4 修正后的建议

1. **升格id 进布局岛 A0 契约**（独立于 G1–G3，且应先于 A1/A2 实施——它改变 centers 元数据结构，晚做要迁移旧文件）
2. 多文件聚合**降级为后选**：触发条件 = 出现 ≥2 条真实「一份子树进多个视图」或「独立分享子树」摩擦（遵循自用摩擦驱动纪律）；若启动，聚合态编辑按 §10.1 多控制器路由实施，attach 条目同样携带 cid（doc+cid 寻址）
3. G4–G6 决策门保留，但优先级让位于升格id 契约评审
