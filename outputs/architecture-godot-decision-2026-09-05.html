性能边界：不是简单的 SVG vs GPU

  • 森林路径明确跳过 LayoutCache，每次全量重算。
  • 自由边先裁剪再路由，但可见集随平移变化，可能触发路由重算与跨边评分变化。
  • 端点包围盒不等于曲线真实包围盒；大弧外鼓仍有误裁风险。
  • Canvas scene 仅接简化节点和树边，自由边被 !useCanvas 条件排除，不能视为等价后端。

Godot 能做，但现阶段不经济

它提供场景变换、动画、2D/3D渲染与原生打包，但不提供本项目现成的协议、锚一致性、事务撤销与浏览器目录权限。

维度现栈局部修正Godot 主客户端
中心 / 引用语义必须修仍必须修：共担成本
布局 / 避障复用移植或桥接
中文编辑 / DOM 面板复用与补回归重建或双UI同步
Web 文件权限授权与降级不会自动越过浏览器沙箱
导出与测试已有基础重做适配，复用领域样例
持续维护面TypeScript / React额外引擎、语言与构建管线

不以沉没成本绑架决策。应该比较未来新增工作与收益。现有 kernel 可经 JS 桥复用，但不等于 Godot 原生部署也能免费沿用。

Web 限制必须按版本说清

所查 Godot 4.6 官方文档：WebAssembly + WebGL 2.0 / Compatibility；Godot 4 的 C# 项目不能导出 Web；单线程可用且默认，多线程才涉及跨源隔离等要求。

官方 Web 导出文档。本报告没有运行 Godot 对比压测。

反转条件：原生/3D/高动态成为核心需求；同数据同功能的原型明显胜出；中文编辑、导出、保存、撤销全过；团队接受双栈维护成本。不是看到更多节点或更炫动画就迁移。

先修发布阻断，再扩功能

优先级改造关键验收
P0文档根与布局根分离部分/全部升格后，关系边与诊断不丢
P0中心资格及投影唯一性一级中心约束贯穿入口与读取；布局ID不重复
P1引用迁移、中心拖拽事务一次拖拽一次undo，Esc取消，改名/移动不误指
P1后端能力清单、资产宿主不静默省功能；保存关闭重开资产仍有效
P2路由缓存、中心缓存、命令注册有性能/维护证据才做，不引入大DI层

粗规划：P0与回归约2–5人日；拖拽/引用闭环约4–10人日；目录宿主约3–8人日。不是承诺，也不能简单相加。Godot 5–10人日仅够对照原型，等价迁移仍是数周至数月级评估。

性能选型的下一次证据

同一批 500 / 2,000 / 10,000 节点，配真实分布的关系边、长文本与附属区；分别测布局、路由、渲染、交互的 p50/p95、内存及空闲CPU。先缓存/批处理，再对等比较现有后端，最后才评估其他引擎。

最终建议：改局部结构，不改产品根基。让多中心成为可靠的文档视图，比迁移 Godot 更接近下一阶段目标。
