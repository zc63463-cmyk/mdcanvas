# PG（project-graph）「自由生成子节点方向」功能审查

日期：2026-09-05 · 对象：本地研究仓库 `E:\Development\MyAwesomeApp\_research\project-graph` @ `1d36fbbe`（与上游 HEAD 一致）
结论：**已实现**，且是三层完整模型；但其方向编码方式与 mindcanvas 架构原则不兼容，不建议照搬其 per-edge 几何模型。
修订（2026-09-05 晚）：用户确认「思想分叉」真实需求 + 节点实体化路线，§5 已更新为**子节点 note.dir 声明模型**（D1′–D4′，约 2–3.5 人日）——数据层确如用户所言「只是一个属性」，真实成本在布局分组调度。

## 1. 结论与证据链

PG 的「自由生成子节点方向」**已经实现并正式发布**，由三层构成：

### ① 预方向（生长预设，UX 层）
- `KeyboardOnlyTreeEngine.changePreDirection`（keyboardOnlyTreeEngine.tsx:263）：给选中节点设「预方向」
- 快捷键：`W W` / `S S` / `A A` / `D D`（shortcutKeysRegister.tsx:2105–2146，zh_CN.yml:1710–1725 有正式文案）
- 设方向后有节点边缘亮线特效提示（`addNodeEffectByPreDirection`，:275）
- Tab 生长（`onDeepGenerateNode`，:293）按 `getNodePreDirection` 决定子节点创建方位；未设置时按入边多数方向推断，根默认 right（:118–148）

### ② 方向持久化在边（数据层）
- `Edge.sourceRectangleRate / targetRectangleRate`（Edge.tsx:95–98）是 `@serializable` 字段——边连在源/目标矩形的哪一侧（归一化 0–1 坐标）随 `.prg` 保存
- `isLeftToRight()` / `isTopToBottom()` 等方向判定由 rate 推断
- **关键机制：预方向只是 UX 预设（会话级 Map，易失），但每次生长会把方向固化进新边的 rate（持久）**——缓存丢了无妨，结果已在数据里

### ③ 布局按边方向分组（布局层）
- `autoLayoutFastTreeMode` DFS 把每个节点的出边分六组：right / left / top / bottom / unknown / nonStandard（autoLayoutFastTreeMode.tsx:623–631），各组子树排对应侧
- **同一节点可同时四向分叉**（扇形树）——这是比 mindcanvas 中心级方向更细的粒度
- `resolveSubtreeOverlaps`（:243–300）解决跨方向子树群重叠：强势方向优先级 right > bottom > left > top，弱势方向被迭代推开（pushCount>1000 兜底防死循环）
- 事后补救：整棵子树方向翻转 `adjustSelectedSubtreesDirection`（:73–98，只翻同轴边 + 父边 + 重新布局），快捷键 `t 4 4` / `t 6 6` / `t 8 8` / `t 2 2`（shortcutKeysRegister.tsx:1991–2029），入历史

## 2. 能力边界（四个缺口）

| 缺口 | 说明 |
|---|---|
| 预方向会话易失 | `preDirectionCacheMap` 无任何序列化路径（全仓库仅 engine 文件引用）；重开项目后回到「按入边推断」。已固化在边里的方向不受影响，影响仅是要重新设一次预设 |
| 方向是几何不是语义 | rate 是浮点对（如 `(0, 0.5)`），「这个子树为什么向左」没有可读语义记录；AI/人读 .prg 无法直接理解方向意图 |
| 非标准边半游离 | unknown / nonStandard 方向的边「保持相对位置不动、不参与规范化」——手动拖过端点的边成为布局不管的飞地 |
| 无所有权概念 | 方向散在每条边上，没有「这棵子树作为一个整体归谁控制」的岛/中心抽象——多方向子树群靠运行时重叠推开，不做所有权预防 |

## 3. 与 mindcanvas 对比

| 维度 | PG | mindcanvas（现状，a3-integration） |
|---|---|---|
| 方向粒度 | **每条边**（同节点可四向分叉） | 每个中心/岛（`centers[].dir`，岛内统一） |
| 编码 | 几何（边 rate，0–1 浮点） | **语义**（`dir: right/left/down/up`，纯文本可读） |
| 持久化 | .prg 二进制（msgpack） | .mm.md 纯文本（人/agent 可直接读） |
| 谁决定普通子节点方向 | 各边自己（生长时固化） | 布局算法按岛 dir 统一决定 |
| 事后改方向 | 子树翻转（改边 + 重排 + 入历史） | 改 centers[].dir（事务 + undo） |
| 重叠处理 | 运行时检测推开（1000 次迭代兜底） | 布局期避让（岛边界 + bounds） |

## 4. 判断：不照搬，但两点可借鉴

**不照搬 per-edge 方向的理由**：
1. 与 centers.ts 的架构原则直接冲突（「节点数据保持纯净，不往节点上挂坐标/方向」——PG 恰恰是把方向挂在每条边上）
2. 同一节点四向分叉在脑图场景是小众需求（XMind 也支持但少有人用）；布局岛已覆盖「多方向」的主诉求——每个岛一个方向，岛数量不限
3. 代价证据就在 PG 源码里：`resolveSubtreeOverlaps` 需要 6 组方向对 × 迭代推开 × 1000 次兜底——这是自由方向真实的复杂度账单

**两点可借鉴**（纳入 cid/后续路线时参考）：
1. **预设-固化分离**：PG 的「预方向（UX 预设，易失无害）→ 生长时固化（持久）」交互很顺。mindcanvas 的 Tab 生长当前沿父岛 dir；若未来支持「下次生长换个方向」，可用同款轻预设，不落文档
2. **子树翻转作为一等命令**：PG 把翻转做成入历史的命令（`t 4 4` 系列）。mindcanvas 改 centers[].dir 已有事务，但「整岛翻转」的 UI 入口（快捷键/菜单项）值得在 C3 阶段一并考虑

### 语义模型：子级声明（每个子节点声明自己挂在父节点的哪一侧）

```markdown
### 中心议题

<!--
dir: left
-->
#### 反方论据        ← 这个子树挂到父节点左侧

#### 正方论据        ← 无 dir = 沿岛/父级方向（右侧）
```

- `note.dir: left|right|up|down`：本节点相对父节点的生长侧；**缺省 = 继承**（最近显式声明 → 岛 dir）
- 同一父节点的子节点按 dir 分组 → 天然实现「思想分叉」（反方向子树各挂一侧）
- 「节点纯净」原则澄清：禁挂的是**坐标/布局状态**（x/y 几何），**语义意图**挂节点有既有先例（via/edge/desc/qa）；dir 属语义意图
- 与实体化正交：实体节点 note 同样可挂 dir；实体锚 centers 解析已修复（2ff0f33）
- 与岛语义的关系：岛 dir 决定岛整体摆放方向；节点 dir 是岛内的局部分叉覆盖——两层不冲突
